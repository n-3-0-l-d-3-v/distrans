# 005 — RPC with idempotent retry

Request/response messaging over the reliable transport, with the one
property a reliable *byte stream* doesn't give you for free: a client
that retries a request (because it couldn't tell whether the first one
was lost, or its response was) must not cause the request to execute
twice.

## Scope
- A request/response framing: request id, method, payload; response
  correlated by request id.
- Client-side retry with backoff when no response arrives within a
  deadline (measured in ticks).
- Server-side idempotency: a dedup table keyed by request id, so a
  retried request that already executed returns the cached response
  instead of re-executing the handler.
- Property test: for an arbitrary sequence of client calls (including
  duplicated/retried ones, arbitrary fault profiles causing the retries)
  against a handler with an observable side effect (e.g. a counter),
  every request's handler runs at most once, and every completed call's
  response matches what that one execution produced.

Not started. Depends on ticket 003 (and typically ticket 004, though RPC
correctness doesn't itself depend on congestion control).
