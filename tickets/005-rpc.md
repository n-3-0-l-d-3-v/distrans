# 005 — RPC with idempotent retry

Request/response messaging over the reliable transport, with the one
property a reliable byte stream doesn't give you for free: a client that
retries a request (because it couldn't tell whether the first one was
lost, or its response was) must not cause the request to execute twice.

## Scope
- [x] A request/response framing over `transport`'s byte stream: a
      length-prefixed reassembly layer (`FrameReader`) since `Connection`
      has no message boundaries of its own, then request id/method/
      payload and response id/ok/payload codecs.
- [x] Client-side retry with backoff when no response arrives within a
      deadline (in ticks) — `RpcClient`, deliberately independent of
      `Connection`'s own reliable-delivery retries (see ADR-005 for why
      that's not redundant).
- [x] Server-side idempotency: a dedup table keyed by request id
      (`RpcServer`), so a retried request that already executed returns
      the cached response instead of re-executing the handler.
- [x] Property test: for an arbitrary sequence of client calls (including
      duplicated/retried ones under arbitrary fault profiles, forced via
      a deliberately short retry deadline rather than only relying on
      loss), every request's handler runs at most once, and every
      completed call's response matches what that one execution
      produced — end to end, over real `channel::Channel`s and a real
      `Connection` pair. Mutation-checked (disabling the dedup table
      fails it immediately).

9 unit tests, 1 end-to-end property test. See
`docs/design/decisions/ADR-005-rpc.md`.
